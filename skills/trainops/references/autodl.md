# AutoDL 配置

仅选择开机模式、配置存储、TensorBoard 或面板时读取；异常恢复见 [协议](protocol.md)。设 `CLI="python3 <技能目录>/scripts/trainops.py -p <实验项目目录>"`。

准备与训练中的代码变更按[本地代码同步](execution.md#本地代码同步)执行；下文的“代码调整”不表示允许在服务器直接修改受版本管理的代码。

## 无卡准备与训练开机

目标是把项目理解、环境配置与代码调整前置到无卡阶段，减少正式开机后 GPU 空等；不是省略 GPU 验证。

无卡模式开机使用的是**本次开机 0.5 核 CPU、2GB 内存、无 GPU** 的配置，不是原实例 CPU/内存规格不变而仅取消 GPU。无卡准备只安排适配该资源的轻量工作：阅读/修改代码与配置、检查路径、语法及少量数据读取；安装、编译和数据加载须限制并发与内存占用。重型编译、全量数据预处理、大模型加载等超出资源的工作，安排到授权且资源充足的环境，或留到有卡阶段补验，并同步待办，不阻塞其他可推进实验。因该资源上限无法完成的检查不等于环境损坏，不反复重试到 OOM，也不擅自超出资源授权升级规格。

开关机由外部 `autodl_mcp` 执行，TrainOps 仅记账。已核对本机实现：适用于普通 AutoDL 容器实例，不适用于 Pro；无卡开机仅支持按量实例。开关机与持续请求须在用户授权范围内；仅启用本技能不构成授权。调用前核实当前 MCP 工具说明；若版本不支持无卡模式或实例不满足条件，说明限制并确认替代方案，不静默改成有卡开机。

| MCP 工具 | 参数 | 结果与边界 |
|---|---|---|
| `instance_status` | `instance_uuid` | 只读查询 `status`、`start_mode` 及 `gpu_name`、`gpu_memory_gb`、`cpu_cores`；关机也可查规格，无需 SSH；无卡运行模式为 `non_gpu` |
| `list_instances` | `instance_uuids=[...]` | 只读批量查询 1–100 个完整 UUID，支持去重、白名单校验和逐项错误；共享一次分页遍历，硬件查询最多 5 路并发 |
| `switch_mode` | `instance_uuid`, `target_mode="gpu"` 或 `"non_gpu"` | 返回 `job_id`；单个后台任务完成关机、确认关机、目标模式开机并复用缺货重试；须确认中断影响，不是可回滚事务 |
| `power_on_no_gpu` | `instance_uuid` | 无卡开机，立即返回 `job_id`，任务中 `no_gpu=true`；不会自动把已运行的有卡实例切成无卡 |
| `power_on` | `instance_uuid` | 有卡开机，立即返回 `job_id`；缺货时后台持续重试，没有另一个“持续开机”工具，也没有每次调用的等待模式参数 |
| `job_status` | `job_id` | 只读即时查询开机/切换任务的 `phase`、`elapsed_seconds`、`attempts`、`suggested_next_poll_seconds`、`error`，不是查询训练进度 |
| `wait_for_job` | `job_id`, `timeout_seconds=15`, `return_on_capacity=True` | 只读等待，终态或 `waiting_capacity` 默认立即返回，指定 120 秒也不硬等缺货；显式 `return_on_capacity=False` 才继续等缺货；超时返回快照；时长支持 0–300 秒，0 为立即查询 |
| `cancel_job` | `job_id` | 只取消后续尝试，不撤销已接受的开机请求，不自动关机；取消后立即查询物理状态，返回 `resulting_status`、`resulting_start_mode`、`resulting_observed_at`，查询失败不改变已取消结论，`resulting_status` 为 `null`、原因见 `resulting_status_error` |
| `power_off` | `instance_uuid` | 先取消活动开机/切换任务，防止后续自动拉起，再请求关机；返回接受结果，不代表关机已完成 |

`instance_uuid` 是平台完整 UUID，不是账本编号 `I01`；从已核实的实例映射取值。MCP 服务名前缀由接入环境决定，不猜完整限定工具名。

**规格用于筛选，不是运行资源证明**：`gpu_name`、`gpu_memory_gb`、`cpu_cores` 来自控制台“规格详情”的配置快照；显存是单卡容量，按 1024³ 字节换算，不能当作多卡总量或当前空闲显存；CPU 是实例分配的 vCPU 数。缺失或无效的可选字段为 `null`，保留待核实，不补 0、不猜型号。可在关机时比较候选实例与实验需求，不为查规格开机或 SSH；无卡阶段仍以 0.5 核 CPU、2GB 内存、无 GPU 为准，不能套用快照规格。实际 GPU 就绪仍须运行态验证。

**等待只观察，不控制任务**：优先 `wait_for_job(job_id, timeout_seconds=15)`，即时看进度用 `job_status`。默认进入 `waiting_capacity` 即返回，不受更长 `timeout_seconds` 影响；及时汇报 `phase`、`elapsed_seconds`、`attempts`、`suggested_next_poll_seconds`，优先推进其他合格实例或准备工作。`elapsed_seconds` 是后台任务耗时，不是训练进度或预计有货时间；`suggested_next_poll_seconds` 是建议下次拉取状态前等待的秒数（单调时钟、向上取整、最小 0；缺货/网络退避时已计入最近一次尝试间隔，约跨两次尝试窗口；`null` 表示无待定等待或任务已结束），不是资源可用倒计时。缺货返回后按该秒数用宿主定时调度器登记一次性唤醒（按[宿主能力适配](hosts.md#定时巡检与资源等待)选择实际工具；Antigravity CLI 为 `schedule`：`DurationSeconds` 取建议值、至少 1 秒，`Prompt` 写明关联任务与 `job_id`，到点先核实是否仍需资源，任务已结束/取消则按[收尾](execution.md#完成或取消收尾)取消后台 job 及关联唤醒，不再开机或续建调度，否则复核 `job_id`；记录宿主任务 ID 与 AutoDL `job_id` 的对应关系及取消入口，登记后继续推进其他任务，没有可推进工作时结束本轮等定时通知），到点再 `job_status`/`wait_for_job` 复核；建议值为 `null` 时不登记定时器，按当前 `phase` 处置。不要用 shell `sleep` 盲等，不在缺货返回后紧密重复默认调用，也不登记高频循环唤醒。宿主没有定时能力时，才在授权范围内用 `wait_for_job(job_id, timeout_seconds=15, return_on_capacity=False)`；`wait_for_job` 单次上限 300 秒，建议值更大时按定时器等待或用 `job_status` 分段复核。单次等待时长不超过用户剩余授权等待范围与调用方工具超时上限（必要时缩短 `timeout_seconds`）；返回后按 `phase` 判断，不把等待超时当作开机失败或成功。等待超时、连接断开或取消等待请求均不会取消后台开机任务，需停止后续尝试时另按授权 `cancel_job`（返回取消后即时 `resulting_status`，稳定态可直接判读，过渡态或查询失败再 `instance_status` 复查）。长轮询不增加上游轮询或开机请求；后台开机重试只查询运行状态，不额外查规格，调用方也不为等结果反复查硬件或重发开机。当前 MCP 未提供该工具时才用 `job_status` 按合理间隔查询，避免密集轮询。

1. **接管并核实**：先 `show --brief`，多实例优先 `list_instances(instance_uuids=[...])`，每批 1–100 个完整 UUID，按实验需求筛选候选；单实例、批量工具不可用或操作后定点复核用 `instance_status(instance_uuid)` 核实目标实例、开机模式与硬件规格。逐项检查结果，失败项保留待核实，不当作实例不存在，不立即重查整批，也不在调用方另编排硬件并发；运行实例再 SSH 检查已有进程。已有训练运行时直接接管巡检，不为无卡准备而打断；已有 GPU 开机且是否可关机不明时先确认，不擅自重启。
2. **无卡准备**：需要远端准备时默认调用 `power_on_no_gpu(instance_uuid)`，保留返回的 `job_id` 并用 `wait_for_job(job_id, timeout_seconds=15)` 等待，按返回 `phase` 确认成功；用 `instance_status` 确认 `status="running"` 且 `start_mode="non_gpu"`。SSH 可达后了解项目结构、训练入口、数据与已有产物，检查环境/依赖、磁盘和路径；执行准备脚本前 `source /etc/network_turbo`，完成配置、代码调整及无需 GPU 的导入、语法、数据读取等检查。无卡阶段不启动 GPU 训练，不把待训练任务标为 running，也不因没有 GPU 就认定环境损坏。
3. **准备就绪后切换**：确认配置与代码已落盘、下载/安装等准备进程已结束、必要产物已保存；确认本次中断已获授权后，已运行的无卡实例优先 `switch_mode(instance_uuid, target_mode="gpu")`，反向切换用 `target_mode="non_gpu"`。已有授权明确覆盖本次操作则不重复询问，否则先确认；已有训练不为准备而打断。切换不是热切换或可回滚事务，由后台任务确认关机后才开机；保留 `job_id`，按上述等待策略观察；关机完成后在 `waiting_capacity` 等卡时取消，`cancel_job` 直接返回 `resulting_status="shutdown"`，不必再查 `instance_status`，过渡态或查询失败才复查。切换活动期间不并行提交同实例的开机或另一切换请求；失败可能已关机，先查真实状态，不盲目重试。工具不支持时才按授权 `power_off` → `instance_status` 确认关机 → `power_on`；`accepted=true` 或 `shutting_down` 均不够，认可的已停止状态是 `shutdown`、`shutdown_by_starting_error`、`shutdown_by_running_error`，遇错误关机先核实原因。这是保留实例与后续训练计划的中间关机，不是释放实例，也不要求“所有流程无后续复用”。尚未准备完成不得提前申请 GPU。
4. **观察训练开机**：上一步已提交切换任务时复用该 `job_id`，不再调用 `power_on`；已关机实例或分步切换确认关机后调用 `power_on(instance_uuid)`；有资源时开机，缺货自动进入后台等待，持续请求不是另一种工具。保留 `job_id`，优先用 `wait_for_job` 等待，需即时进度时用 `job_status`；按返回 `phase` 判断：`waiting_capacity` 表示缺货等待，`waiting_network` 表示网络/限流退避，`queued/checking/starting/confirming` 都不是最终成功，`succeeded` 才是任务确认成功，`failed/cancelled` 须处置。请求已提交不等于开机成功，不循环重发 `power_on`，也不伪造训练进度。超出用户约定等待范围时按授权 `cancel_job`，先看返回的 `resulting_status`：`shutdown`、`running` 等稳定态可直接采用，`starting`、`shutting_down` 等过渡态或 `null`（原因见 `resulting_status_error`）再查 `instance_status`；已发出的电源请求仍可能继续改变状态，不能假定取消后实例已关机；失败且 `error.ambiguous=true` 时先查询实例，不盲目重试。
5. **GPU 就绪再训练**：用 `instance_status` 确认 `status="running"` 且不是 `start_mode="non_gpu"`，再检查 SSH、`nvidia-smi` 及训练框架能否使用预期 GPU；`start_mode` 缺失不能单独作为有卡证据。复核挂载、环境与训练入口，无卡阶段无法验证的 GPU 相关项在此补验。确认依赖满足后，用 tmux/screen 启动正式训练并登记真实状态与进度；若 GPU 验证失败，不启动训练，及时处置，避免 GPU 空转：自愈最多 5 次，仍无法继续即先关机止付，见 [协议](protocol.md#故障自愈与止付关机)。

后台等待由 MCP 进程承担：`AUTODL_MAX_WAIT_SECONDS` 默认 0（不限缺货等待时间），不是 `power_on` 的参数；需要有限等待时与用户约定服务配置或取消时点。后台任务仅保存在当前 MCP 进程中，服务退出会取消任务但不会自动关机，重启后旧 `job_id` 无法恢复；接管先查实例真实状态，不因任务不存在就重发开机。不同模式的活动任务冲突时先按授权取消并核实实例；已运行的不同模式必须先关机，不会原地切换；优先由已授权的 `switch_mode` 完成，不另手工插入开关机。止付仍用 `power_off`，不能用切成无卡代替关机。

**账本与开机模式边界**：实例状态只表示电源/可达性，不区分无卡与有卡；无卡已开机仍登记 `on`，不能用 `off` 冒充“不占 GPU”。持续请求期间按真实电源状态记录，不能仅因请求已提交就标为 `on`。开机模式另用 `--mode` 记录：无卡准备与持续请求等待期间是 `--mode no-gpu`，正式有卡开机是 `--mode gpu`，核实不了就 `--mode none`（未观测）而不是猜。切模式后按实际状态重新登记，两种模式各自独立，不以一个冒充另一个。

```bash
$CLI instance set I01 --mode no-gpu --brief   # 无卡准备/持续请求等待；有卡开机用 --mode gpu
```

## 按需用卡与空闲处置

GPU 资源按开机时间占用，节省重点是减少空转和重复准备，同时尽快交付有效结果，不是把所有实例开满。无卡模式低配：共享准备集中做一次，只有逐机检查、安装差异等确有需要时才开相应无卡实例；控制安装、解压和数据读取并发。重 CPU/内存工作按实际吞吐选择已有授权的充足资源，不为节省 GPU 时间在低配无卡机反复失败或无限拖延。

- **开机前有可执行任务**：先满足真实依赖、数据与代码版本、配置、轻量检查及通知探针；缺卡期间还可能变化的任务在 GPU 开机后再次核实。只将必须有 GPU 才能做的检查、计算留到有卡阶段。规格与挂载可在准备阶段核对，不为查规格开机；不把 GPU 开着等下载、人工回复或外部同步。
- **按就绪工作量申请**：候选实例不等于必须全部开机。只按 GPU/显存、环境、资源可用性、已观测速度及启动/准备耗时分配独立任务。活动开机请求数不超过可独立执行且已准备好的任务所需实例数，并遵守资源授权与并行上限；同一任务只保留一个目标与活动资源请求，不多机竞速抢卡。耗时未知就说明依据与未知，不编造最优排程。
- **全部缺卡仍可推进**：复用已提交的 job，按建议退避登记唤醒；继续本地工作、适量无卡准备和已有结果分析，无事可做就结束本轮等待通知。候选可用性变化时按[多机再平衡](cli.md#单-agent-多机再平衡)改派 pending；原请求须取消并核实物理状态后才替换，防止迟到开机与重复执行。确为不同就绪任务的多个请求可在授权并行度内并行。
- **结束即接续或停机**：按预计完成时间安排执行唤醒，避免等半小时汇报才发现 GPU 空转。任务结束先核实进程与必要产物，立即查看全局是否有可接续的合格任务；可立即启动则复用当前环境，不能则按已有授权关机等待，确有轻量准备才切无卡。即使未来仍会复用，也可保留实例中间关机，不必等所有流程结束；不为等依赖或保留 GPU 占位而无限开机。短暂保留须有明确的近期就绪依据、时间边界并符合资源授权，不能假定关机后仍能拿到 GPU。仅 GPU 利用率低不等于训练停滞，先结合进程、日志与数据加载确认，正常训练不为节省资源擅自中断。

关机/切模式仍须在已有授权内，且核实本实例没有其他任务或准备进程受影响；不足则及时请求一次决策，说明空闲原因、资源持续占用风险与建议，不静默等待。停机前保存必要产物、取消不再需要的开机/切换 job，按物理终态记账；不擅自释放实例。最终收尾与故障预授权保持原边界，见[恢复与关机](protocol.md#恢复与关机)。

## 三盘与用量

| 路径 | 保留边界 | 内容 |
|---|---|---|
| `/` 系统盘 | 关机保留，随镜像保存；容量小且与系统共用 | 代码、conda 环境、配置脚本 |
| `/root/autodl-tmp` 数据盘 | 快；关机保留，不随镜像保存，释放实例即丢 | 数据集、checkpoint、TensorBoard 事件、高 IO 临时产物 |
| `/root/autodl-fs` 文件存储 | **同一账号下所有实例共享同一份**，不受开关机/保存镜像影响 | 最终权重、评测结果、需共享或长期保留的数据 |

**`/root/autodl-fs` 对所有实例是共享的**：同一账号下的每个实例挂载的是同一份文件存储，任一台写入，其余实例立刻可见——不用在实例间互传或 scp。据此安排两件事：跨实例交接直接落在它上面（只需上传一次的数据集、对照实验共用的输入、需要汇总的评测结果），各实例按自己的编号建目录（如 `/root/autodl-fs/<项目名>/F01-T02/`），几台同时往同一路径写会真的撞在一起，覆盖或互相删除都发生在共享盘上；反过来，清理共享盘前先确认不是别的实例或别的实验正在用的产物，别只按本实例视角判断。

共享输入按版本集中存放并只读复用；下载、解压、预处理采用单写者，写临时路径，完整性校验后再发布完成标记或原子改名，其他任务不读取半成品。复用前核对数据版本/划分、预处理参数、代码与产物完整性；只读基线可复用，需独立训练的实验不能拿同一权重冒充独立结果。输出按任务/Run 隔离，环境安装不可多机并发改写同一目录，且共享文件不表示 Python/CUDA 环境可跨机直接复用。训练 IO 成为瓶颈时可按授权提前缓存到各机数据盘；这是本地缓存，不是重复下载或全量跨机同步。

释放实例前先将保留产物同步到文件存储或下载本地，并核实转存结果。不要把临时产物长期堆在文件存储。

```bash
ssh <别名> 'df -h / /root/autodl-tmp /root/autodl-fs'
$CLI instance set I01 --disk "sys:12/30,data:40/50,fs:5/200" --brief
```

用量单位 GB。--disk 逐盘合并，没提到的盘不动；`data:none` 清空该盘。用量达到 90% 时 show 的盘行带 `!`，check/show --brief 有提醒；先核实、清理或扩容再开任务。满盘处置见 [协议](protocol.md#磁盘处置)。

## TensorBoard

每次训练前检查项目的训练入口、配置和日志组件；项目已有 TensorBoard 配置就必须实际使用，启用相应 logger/开关，沿用项目已有指标与记录方式。启动后核实本次 run 的事件文件实际产生并随训练更新，巡检时检查持续写入；缺失或停更先排查配置、依赖与写入路径，不能只启动 TensorBoard 服务就视为已使用。接管已有训练先核实事件记录和服务，避免重复启动。

事件文件写数据盘，用软链接入内置读取目录，不要写满系统盘：

```bash
TB=/root/autodl-tmp/tf-logs/<项目名>
mkdir -p "$TB" /root/tf-logs
ln -sfn "$TB" /root/tf-logs/<项目名>
# 每个任务独立 run，例如 "$TB/F01-T02"
tensorboard --logdir "$TB"  # 确需独立服务时，由调用方管理后台进程
```

换 logdir 前先定位并核实本项目 TensorBoard 进程，按授权停止后重启；不要批量杀掉所有 TensorBoard。自定义服务可用 `--port 6007` 从 AutoPanel 进入；需要公网直链时使用 `--port 6006 --host 0.0.0.0`（平台映射 6006/6008），确认用户允许对外访问。计划不记录 TensorBoard 路径/链接，保存在远端脚本中。

## 面板

收到实验任务后随即起，作为用户在浏览器里看执行队列与进度的界面；`serve --port 8765` 本机监听 http://127.0.0.1:8765，把地址报给用户。**它必须以后台常驻任务运行**：用 harness 自己的后台任务机制起，既不要占着前台，也不要用 shell 的 `&`——面板是那次 shell 调用的子进程，父 shell 一退（命令跑完收尾、会话切换都算）进程就被带走，用户页面直接失联。CLI 自己不后台化、不写 PID 文件、不注册系统服务（不碰 systemd）：常驻与日志都归起它的调用方。后台任务活在 harness 进程里，harness 一退面板就没了——重开前先确认旧面板没有在跑（端口被占说明面板已在跑，别重复起）。页面仅以执行队列展示任务与进度，不展示磁盘条或 TensorBoard 链接。

面板只读：只渲染执行队列与进度，不提供业务写入入口。
