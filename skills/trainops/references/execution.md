# 执行与通知闭环

开工、修改代码、巡检及完成/取消时读取。本文约束 agent 使用现有 SSH、MCP 与宿主调度能力，不给 TrainOps CLI 新增训练执行器、通知服务或常驻调度器；原有计划、无卡准备、多机调度、五次自愈止付和实验日志流程不变。

TrainPilot 的全部 MCP 工具、实时协议、异常指令与下一任务回执见[TrainPilot MCP 监督闭环](trainpilot.md)，使用通知链路前必读。

## 即时状态通知

三条通道职责独立，不能相互顶替：

- **MCP `trainpilot`**：主动推送任务状态，让用户不在屏幕前也能即时获取训练状况。
- **`lark-cli` 实验日志**：记录 Run、配置变化、真实指标和证据，用于对照与迭代分析；仍按[实验日志](experiments.md)先读后写。
- **任务面板与当前对话**：展示计划、进度、费用和操作回执。更新面板、写表成功或对话回复均不等于已发送 `trainpilot` 通知。

1. **开工检查**：确认 AutoDL MCP、MCP `trainpilot` 和目标 SSH 的可用性；工具名与参数以当前实际工具说明为准，不猜完整限定名。缺工具、授权或连接时说明实际阻塞与影响，不声称操作或通知成功。通知不可用不静默改用实验日志冒充推送；向用户说明并确认替代通知方案，不阻断安全处置或关机止付。
2. **固定巡检**：训练进入 running 后，按[入口](../SKILL.md#日常闭环)实际创建整点/半点宿主调度任务；记录任务标识、覆盖的训练任务/实例与用途，资源等待的一次性唤醒也记录对应 `job_id`。不得只承诺定时检查；工具不可用或会话生命周期不足以持续调度时，说明限制并与用户确认可用方案，不得声称已建立持续监控。新会话先核实已有调度，不重复创建。
3. **每次巡检**：通过 SSH 和 AutoDL 真实检查实例状态、训练进程、GPU 使用情况、日志是否持续更新、训练进度、可获取的关键指标、异常和下一步动作。无法获取的项明确标为未知，不编造指标；仅进程存活不能证明训练正常推进。更新真实计划状态，按实验日志流程留痕，并通过 MCP `trainpilot` 与当前对话汇报，不能只写 `--checked`。
4. **重大节点立即额外通知**：开机成功、代码同步完成、训练启动、阶段完成、评估完成、训练失败或异常中断、恢复运行、任务完成及关机完成，不等下一次固定巡检。说明对应任务/实例、真实结果及下一步；失败通知附已核实证据。通知只含脱敏摘要和必要引用，不发送凭据或完整敏感日志。
5. **发送结果核实**：依据实际工具返回区分事件记录与通知送达；`report(success=true)` 不等于飞书已送达，`completed/failed` 不单独发卡，终态及最终推送按[TrainPilot 协议](trainpilot.md#状态上报与飞书送达边界)处理；失败如实报告并在后续可用时补报，不密集重试、不把失败算成训练自愈次数，不为发送通知延迟必要的止付和产物保护。实验日志同步失败也不能阻断即时通知。

## 本地代码同步

需要修改具体代码时执行以下顺序；无代码变更时核对已有版本即可，不创建空提交或无故推送。

1. **核实目标与工作区**：确认本地和服务器对应的仓库、分支、提交版本及未提交修改；保留用户已有工作，不夹带无关改动。实例 UUID 与 SSH 别名必须来自用户明确提供或项目已有且已核实的映射，缺失或有歧义先询问，不猜测其他机器；连接信息变化后先核对实际 SSH 目标。
2. **本地修改与验证**：在本项目本地工作区修改代码和配置，完成适用检查，保留修改记录。资源不足的验证按无卡/有卡阶段分配，不虚报已通过。**不在服务器直接修改受版本管理的代码**，无卡准备中的代码调整也遵守此规则。
3. **提交并推送**：只提交任务相关变更，记录实际 commit，再推送到对应远程分支；具体任务已授权本链路的提交推送才执行，否则先取得授权，不把仅加载插件当成授权。不覆盖用户未提交工作、不强制推送；遇到冲突或权限问题先核实并报告，不跳过同步直接训练。
4. **远端拉取并核对**：服务器对应仓库拉取已推送版本，再核实仓库、分支与 commit 一致，且没有未说明的工作区差异；有冲突不强制覆盖。每次远程执行准备/训练脚本前，在远端 Bash 执行 `source /etc/network_turbo`，不是本机初始化命令。核对通过才执行，并立即通知代码同步完成。
5. **可恢复启动**：用 tmux/screen 等 SSH 断开后继续运行的方式启动；先排除重复进程。在远端本项目可定位的启动记录中保存会话或进程标识、日志路径、输出目录、实际启动命令与 commit，敏感参数脱敏；在 Run 的 `config_path` / `artifacts` 中留必要引用，不向 `plan` 塞命令和日志。已有未提交变更的接管记录可保留配置快照与 patch 证据，但不是允许绕过上述同步流程的新修改入口。

## 完成或取消收尾

任务完成或用户取消后必须执行最终闭环；部分任务结束时仅收尾对应范围，不影响其他仍在运行或等待的任务。

1. **核实进程与产物**：完成时确认训练及相关子进程退出、结果与 checkpoint 已保存；取消时按授权结束本任务进程并保留必要产物，结果未知先核实，不虚标 done。失败保存诊断信息，故障恢复与止付仍按[协议](protocol.md)执行。
2. **更新计划与实验日志**：按真实结果登记 done / cancelled / failed / blocked，先读 Run 再 update / sync，保留证据；飞书失败保留本地 pending 并报告，不阻断后续资源清理。
3. **清理本任务调度与等待**：核对创建时记录的任务标识，删除或取消本任务创建且不再需要的定时巡检、资源等待唤醒；同时按授权 `cancel_job` 停止不再需要的 AutoDL 后台开机/切换尝试。取消宿主唤醒不等于取消 AutoDL job，`cancel_job` 也不等于关机，须判读其返回物理状态，过渡态或查询失败再核实。共享巡检仍覆盖其他活动任务时保留并更新范围，不清理其他任务的调度；清理失败明确列出残留及影响，不声称全部完成。
4. **实例最终状态**：按已有授权、其他训练和后续复用情况处置实例；满足最终关机条件时及时关机并核实物理终态。不得关闭仍有其他任务运行的实例，不因任务取消就无条件关机；无授权时明确报告实例仍在运行及待确认事项。关机规则与五次自愈止付预授权保持不变，见[恢复与关机](protocol.md#恢复与关机)。
5. **最终汇报**：通过 MCP `trainpilot` 和当前对话汇报任务最终结果、结果/checkpoint/诊断信息的真实位置、实例最终状态（仍在运行则说明原因）、调度与等待清理结果，以及未完成事项和所需决策。通知失败按上节处理，不能把对话回复当作推送成功。

**任务面板可以保留**：不把完成/取消收尾解释为必须停止 `serve`，也不强制清空计划、删除 Run 或关闭其他任务的巡检；面板继续按原有生命周期与结算规则运行。
